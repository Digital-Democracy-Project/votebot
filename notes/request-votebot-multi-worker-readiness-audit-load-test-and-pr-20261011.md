Facts below are what I read or measured on 2026-10-11; my code reading was a quick grep, not a review, so treat the "hazards" as leads to verify.

## 1. How it runs today (production host, `m6a.xlarge`)
- **One uvicorn process.** The image's command (`infrastructure/docker/Dockerfile`, line 63, production stage) is `uvicorn votebot.main:app --host 0.0.0.0 --port 8000`; the compose service `votebot` (`infrastructure/docker/docker-compose.prod.yml`) adds no command, no `--workers`, **`mem_limit: 768m`** and no CPU limit (`container_name: votebot-ddp-next`, networks `default` and `broker`, logs on a bind mount). Image `votebot-ddp-next:local` = `d3742ae`.
- **Measured now (20:13 UTC, no chats):** 1 process, 7 threads, **126 MiB of 768 MiB**, **0.1 percent CPU** (a 19 percent reading right after the boot was a startup artifact). **I have no number under load.**
- **The host:** 4 vCPUs (2 physical cores, 2 threads each), 15.3 GiB, about 10 GB available. Other services share it: broker `web` gunicorn **5** sync workers, api-v3 gunicorn **4**, celery **4**, ddp-sync 1 uvicorn process. (Details: `reply-worker-counts-across-all-services-web-now-5-and-the-deploy-request-hash-moved-20261011.md` on the broker branch.)
- **uvicorn reads `WEB_CONCURRENCY`** (its default for `--workers`) if no flag is given.

## 2. What changing the count involves on this host
1. **The setting has to come from the repo.** `.env` is rendered in full by `infrastructure/render-env.sh` from AWS Secrets Manager plus `infrastructure/docker/prod.env.defaults` (the file's own header: "the script rewrites .env in full, so a change to any line below ... is made HERE, by a PR"). A hand edit of `.env` on the host would be overwritten on the next render. So the worker count belongs in `prod.env.defaults` (or the compose `environment`/`command`).
2. **The memory limit has to go up.** 768 MiB is a hard limit. At about 126 MiB idle per process plus the caches below, 4 workers would be at or over it, and under load a worker would grow. Please size it from your measurement, not from my idle number.
3. **Deploy mechanics (mine):** `git pull`, rebuild (`docker compose -f infrastructure/docker/docker-compose.prod.yml build votebot`), re-run `render-env.sh` if the defaults file changed, then `up -d --no-build --force-recreate votebot`, with a rollback tag of the running image (`votebot-ddp-next:d3742ae`). I will check there are no chats first.

## 3. Multi-worker hazards I found (file and line on `d3742ae`; please verify each)
- **The big one: websocket sessions live in a per-process in-memory manager.** `src/votebot/api/routes/websocket.py` has a connection manager with `get_session(session_id)` (line 109) and per-connection state dicts (lines 73 to 84: conversation counters, intents, handoff flag). The Slack human-handoff code looks sessions up there (`get_session_for_thread` from Redis gives a session id at lines 208 and 265, and `self.get_session(...)` at lines 142, 183 and 230 reads this process's memory; `publish_agent_event` at line 216 goes through Redis). **With several workers, a Slack agent's reply could arrive at a worker that does not hold the visitor's websocket.** Slack is off today (it is added on cutover day with `render-env.sh --with-slack`), so this would only bite after cutover; please say whether the design already handles it (for example every worker receives the pub/sub event and only the owner delivers).
- **Per-process singletons (each worker would have its own copy):** `config.py:206` settings (`@lru_cache`); `services/embeddings.py:175` `EmbeddingService`; `services/web_search.py:272` `WebSearchService`; `services/redis_store.py:359` Redis store; `services/button_cache.py:228` button cache and `:243` its invalidation pub/sub subscriber (fine: invalidations reach every worker); `utils/federal_legislator_cache.py:338` and `core/retrieval.py:19` (an in-memory federal legislator cache, loaded over HTTP with a 30 s timeout: N workers would each load it, and N times the memory); `utils/metrics.py:209` `MetricsCollector` (a global collector with no `/metrics` route that I found: counters would be per worker, so any reading would show one worker's share).
- **Startup work runs in every worker:** `main.py` lifespan (line 62) runs `reconcile_on_startup` (lines 78 to 84, a scan of Redis for stale button-cache entries) and starts the invalidation subscriber (line 88). Probably harmless and idempotent; please confirm two workers cannot delete each other's fresh entries.
- **Query log files:** `get_query_logger()` (used at `websocket.py:417`) writes under `QUERY_LOG_DIR` (`/opt/votebot-logs/queries`, one file per day; old files are handled by `infrastructure/query-log-cleanup.sh`). Please confirm several processes appending to the same daily file cannot interleave or truncate lines.
- **Blocking calls:** the HTTP code uses `httpx.AsyncClient` throughout (good); I could **not** confirm from my grep whether the OpenAI and Pinecone calls are async or run in threads. A blocking call on the event loop stalls every chat on that process, and that is the real choke point for one process, more than the number of requests.
- No in-memory rate limiter found (the only "rate limiting" hits are the federal cache and the OpenStates client).
