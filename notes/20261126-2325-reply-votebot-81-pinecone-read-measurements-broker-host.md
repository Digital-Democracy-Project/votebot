# Reply (read-only): VOTEBOT-81, what one Pinecone read costs and how many ran; the broker host, 11-26 23:25 UTC

Host and method: the broker host (EC2). I used the services' own clients from inside their containers (the broker's web container and `votebot-ddp-next`). **Total live reads made: 2 queries (one per shape) and 2 `describe_index_stats` calls, plus one embedding call for the broker's query and one for the chat's.** Nothing was written, restarted or changed. No key is shown. The legacy VoteBot 2.0 server is not on this host ("not my host").

## 1. Size of one read (response body bytes)
* **The broker's search query** (its own `semantic_search` helpers: `topK` 100, metadata on, values off, filter `document_type` in the broker's `SEARCHED_DOCUMENT_TYPES`, query "school funding"): **536,986 bytes, 100 matches, about 5,370 bytes a match.** Index `ddp-knowledge-base`, namespace `default`. **`SEARCHED_DOCUMENT_TYPES` is `bill-text` and `bill-votes`** (not the three types in your note). By the code's own docstring, **every search that reaches the semantic leg makes two Pinecone queries**; I measured one, so a search can cost up to about **1.07 MB** if the second is the same size (the second query's size is not measured).
* **The chat's query** (the 3.0 container's own `VectorStoreService.query`, `top_k` 10, metadata on, query "school funding"): **57,345 bytes for 10 matches (about 5,700 bytes a match).** At that size the chat's usual 56-match read is about 320 KB and a 100-match bill lookup about 570 KB (arithmetic, not measured). The container's index reports the **same vector count (504,897) as the broker's index**, so I take them to be the same index; I did not print the chat's index name.
* **`describe_index_stats`:** **149 bytes**, **1 namespace**, 504,897 vectors (same answer from the broker's and the chat's side).

## 2. How many reads ran
* **The 3.0 chat server on this host** (its log reaches back to its start, **11-20 14:20 UTC**): **133 "Querying Pinecone" lines in total: 73 on 11-20, 16 on 11-21, 11 on 11-23, 33 on 11-26 (includes the VOTEBOT-77 probes and my one measurement); none with `top_k` 100; 53 chat messages.** Even at the 100-match size that is under 80 MB: **this server is not where the 10 GB went.** (4,988 WebSocket connects in the same window are the widget connecting, not chats.)
* **The broker's searches: I cannot count them from here.** nginx's log only reaches back to 00:45 UTC today (I recreated it for the release) and it holds **no `/api/search` request at all**: the website's server calls the broker on the internal network, not through nginx. Gunicorn has no access log, and the web log has no semantic lines. So no per-day count, no top callers.
* **The broker's limits, as deployed:** `SEARCH_SEMANTIC_ENABLED` is **true**; the two rates are the **defaults (30 a minute per client, 1,000 an hour global)**; the counters live in Django's **Redis cache (shared)**, not per-process; **no `--workers` flag and no `GUNICORN_CMD_ARGS`**: `docker top` shows 6 gunicorn processes (one master plus about 5 workers). **Ceiling arithmetic (estimate, not measured):** 1,000 semantic searches an hour at 0.54 to 1.07 MB each is 0.54 to 1.07 GB an hour, so the 10 GB monthly cap is about **9,300 to 18,600 searches** in a month, or **10 to 19 hours at the ceiling**.
* **The stats call:** **ddp-sync on this host** calls Pinecone about every 30 s: roughly **95 to 118 `describe_index_stats` calls an hour** (118 at 22:00 UTC; 353 "list indexes" calls in 3 h), 149 bytes each, **about 17 KB an hour: negligible egress**. I did not identify which ddp-sync module does it. The chat container's own health check does not call Pinecone's stats in what I read.
